# 백엔드 기술 표준 가이드에서 **"왜 모든 API에 POST 방식을 강제하는가?"**에 대한 논리는 개발팀의 설득과 보안 심의 통과를 위해 매우 중요

<br>
<br>

## 1. 쿼리 스트링 정보 유출 방지(Query String Information Leakage)

가장 큰 이유는 **데이터 노출 차단**입니다.

``GET``방식은 데이터를 URL에 포함하지만, ``POST``는 메시지 바디(Body)에 캡슐화합니다.

- **브라우저 히스토리 보호**: ``GET``요청 시 URL에 포함된 민감한 파라미터(고유 식별자, 검색어 등)가 브라우저 방문 기록에 그대로 남는 것을 방지합니다.

- **서버 로그 보안**: Nginx나 Apache 같은 웹 서버 로그에는 요청 URL이 기록되는데, POST를 쓰면 로그 파일에 실 데이터가 찍히는 것을 원천 차단합니다.

- **Referer 헤더 유출 방지**: 우리 사이트에서 외부 링크로 이동할 때, 이전 페이지의 URL(파라미터 포함)이 외부 서버로 전달되는 것을 막습니다.

<br>

## 2. 메시지 터널링 및 보안 가시성 (Message Tunneling)

모든 요청 형식을 POST와 JSON으로 단일화하는 전략입니다.

- **WAF(웹 방화벽) 효율 극대화**: 보안 장비가 검사해야할 대상을 "POST" 요청의 Body"로 고정할 수 있습니다.

- **페이로드 암호화 용이**: 클라이언트와 서버 간의 데이터를 암호화하여 주고받을 때, URL 형태보다는 JSON 바디 형태가 암호화/복호화 로직을 적용하기 훨씬 수월합니다.

<br>

## 3. 데이터 구조의 유연성 및 제약 해소

- **URL 길이 제한(URL Length Limitation) 회피**: 브라우저나 프록시 서버는 URL 길이에 제한 (보통 2,048자 내외)이 있습니다. 복잡한 검색 조건이나 대용량 필터링이 필요한 list 조회 시 POST를 쓰면 이러한 제약에서 자유롭습니다.

- **객체 지향적 데이터 전송**: GET은평면적인 구조만 보낼 수 있지만, POST는 JSON을 통해 계층 구조(Hierarchy)를 가진 복잡한 객체를 그대로 전달할 수 있어 현대적인 백엔드 아키텍처에 적합합니다.

<br>

## 4. 캐싱으로 인한 데이터 오염 방지

- **강제적 신선도 유지**: GET요청은 브라우저나 중간  캐시 서버(CDN 등)에서 임의로 결과를 캐싱할 수 있습니다. 보안이 중요한 비즈니스 데이터의 경우, 실시간성이 보장되지 않거나 타인의 조회 결과가 노출될 위험이 있습니다.
POST는 기본적으로 캐싱되지 않으므로 항상 서버의 최신 상태를 보장합니다.
